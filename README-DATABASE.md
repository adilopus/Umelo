# База данных UMELO — план перехода с localStorage на PostgreSQL

Этот документ и файлы рядом (`prisma/schema.prisma`, `docker-compose.yml`,
`.env.example`) — конкретная подготовка к переходу от текущего клиентского
демо (всё в `localStorage` браузера) к настоящему бэкенду. Ничего из этого
пока **не подключено** к работающему приложению — это стартовый комплект для
разработчика, когда команда будет готова поднимать бэкенд.

## Почему сейчас так, а не сразу с БД

Демо строилось как чистый фронтенд без бэкенда специально — чтобы быстро
проверять UX-гипотезы и дизайн без затрат на инфраструктуру. Для этого
localStorage был правильным выбором. Но у него есть жёсткий потолок:

- один браузер = один "пользователь", нет реальной многопользовательности;
- лимит ~5–10 МБ на домен (уже ловили `QuotaExceededError` из-за фото);
- любое бизнес-правило (лимит бесплатных откликов, списание билетов) можно
  обойти через консоль браузера за 10 секунд — доверять этому нельзя, когда
  на кону настоящие деньги (билеты/подписка);
- нет истории операций, нет бэкапов, нет доступа с другого устройства.

## Рекомендуемая архитектура

| Слой | Технология | Зачем именно так |
|---|---|---|
| Основная БД | **PostgreSQL** | ACID-транзакции (списание билета + создание отклика — атомарно), реляционные связи, полнотекстовый поиск и геолокация (PostGIS) из коробки |
| ORM | **Prisma** | Типобезопасные запросы, миграции из коробки, схема почти 1-в-1 ложится на уже существующие TS-типы в `lib/types.ts` |
| Кэш / лимиты / real-time | **Redis** | Дневной лимит откликов мастера, рейтинг блогеров (Sorted Set — готовая структура ровно под топ-10/50/100), pub/sub для чата |
| Файлы (фото/видео/документы) | **S3-совместимое хранилище** | Убирает лимит по размеру и саму причину прошлого бага с base64/`NaN` — фото хранятся вне БД, в заказе/статье только ссылка |
| Хостинг | **Один бюджетный VPS с self-hosted Postgres+Redis в Docker** | Managed-БД у облаков стоит заметно дороже голого VPS на этапе MVP — дешевле поднять контейнеры рядом с приложением и снимать бэкапы по cron |

### Хостинг и стоимость (российский рынок, минимум вложений)

- **VPS**: Timeweb Cloud, Selectel, RUVDS или VK Cloud — 2 CPU / 4 ГБ ОЗУ
  хватает с запасом на старте (Postgres + Redis + само приложение в одном
  `docker-compose.yml`, который уже лежит рядом с этим файлом).
- **Объектное хранилище**: Яндекс Object Storage или Selectel S3 — оба
  S3-совместимы "из коробки", работают с обычным `aws-sdk`/S3-клиентом,
  платите только за реально занятые гигабайты.
- **SMS для входа по телефону** (типично для российского рынка): SMS.ru,
  SMSC.ru или Green SMS — любой на выбор, интерфейс подключения похожий.
- Managed Postgres/Redis от тех же облаков можно подключить позже, когда
  вырастет нагрузка и понадобится готовое HA/failover без самостоятельной
  настройки репликации — на старте это не нужно и стоит дороже.

## Схема данных

`prisma/schema.prisma` — 14 моделей и 8 enum'ов, перекладывающих текущие
TypeScript-типы в реальные таблицы. Ключевые отличия от клиентской модели
(не один в один, а с исправлением того, что в демо было упрощено):

- **`ticketsBalance` было одним числом** — теперь `TicketTransaction` — учётная
  книга (ledger): баланс = сумма всех транзакций, а не поле, которое можно
  случайно испортить конкурентной записью. Заодно появляется история для
  поддержки ("куда делись билеты").
- **Дневной лимит бесплатных откликов** был клиентским состоянием (обходился
  через консоль браузера) — теперь `FreeResponseUsage` считается на сервере
  по реальным строкам в БД, подделать нельзя.
- **Медиафайлы** (`OrderMedia`, `OrderDocument`) хранят не base64, а ссылку
  на объектное хранилище — тот самый источник прошлого бага с переполнением
  `localStorage` исчезает архитектурно, а не заплаткой.
- **`AdminUser` как отдельная таблица** больше не нужна — администратор
  теперь просто `User` с `role = ADMIN`; бан/удаление — обычный `UPDATE`/
  `DELETE` по `User`.
- **Координаты (`latitude`/`longitude`)** добавлены в `Order` — в демо
  `distanceKm` был захардкожен нулём; с этими полями и расширением
  **PostGIS** расстояние до заказа считается по-настоящему.

Схема проверена структурно (парность скобок, все связи ссылаются на
существующие модели и поля — без разрывов). Прогнать `prisma validate`
через официальный CLI в этой песочнице не удалось: движок Prisma качается
с `binaries.prisma.sh`, а этот домен недоступен в текущей сетевой политике
инструмента. На вашей машине с обычным доступом в интернет команда:

```bash
npx prisma validate --schema=prisma/schema.prisma
```

сработает штатно за секунды.

## Путь миграции — по шагам

1. **Поднять инфраструктуру.** `cp .env.example .env`, заполнить пароли,
   `docker compose up -d` — поднимет Postgres и Redis на VPS.
2. **Прогнать первую миграцию.**
   ```bash
   npm install prisma @prisma/client
   npx prisma migrate dev --name init
   ```
   Это создаст все таблицы из `schema.prisma` в реальной БД.
3. **Написать backend-слой.** Проще всего — API Routes/Route Handlers прямо
   в этом же Next.js-проекте (`app/api/*`) — отдельный сервис на старте не
   нужен, Next.js полноценно full-stack.
4. **Перенести бизнес-логику на сервер**, а не только данные: списание
   билетов, дневной лимит откликов, проверка пароля — сейчас это клиентские
   функции в `lib/store.ts`, их нужно продублировать (а по сути — перенести)
   в API-хендлеры, иначе смысла в БД для доверия к балансу не будет.
5. **Заменить persist zustand на реальные запросы.** Сам zustand-стор можно
   оставить для UI-состояния (открытая вкладка, черновик формы), но данные
   (заказы, статьи, баланс) должны приходить с сервера — удобно завести
   React Query/SWR поверх текущих компонентов, меняя источник данных
   постепенно, компонент за компонентом, не переписывая всё разом.
6. **Загрузка файлов** — заменить `compressImage()` (сжатие в base64 на
   клиенте) на реальную загрузку в объектное хранилище через presigned URL:
   клиент получает с сервера временную ссылку для загрузки, грузит файл
   напрямую в S3-хранилище, серверу передаёт только итоговый URL.
7. **Настоящая авторизация.** Пароли — только хэш (bcrypt/argon2), сессии —
   JWT или БД-сессии, вход по телефону — через SMS-провайдера из `.env`.

Мигрировать можно постепенно, не останавливая разработку фронтенда — схема
и docker-compose уже готовы, стартовать можно в любой момент.
