# UMELO — стартовый PWA-проект / адаптивный веб-сайт

Кликабельная демо-версия ключевого сценария сервиса на Next.js 14 (App Router) +
Tailwind CSS. Данные хранятся в браузере (localStorage через zustand), бэкенда нет —
это фронтенд-прототип для проверки UX и питчей, с которого удобно наращивать реальный API.

> **Планируете реальный бэкенд?** См. [`README-DATABASE.md`](./README-DATABASE.md) —
> готовая Prisma-схема (`prisma/schema.prisma`), `docker-compose.yml` для
> self-hosted Postgres+Redis на бюджетном российском VPS и пошаговый план
> миграции с localStorage.

## Каталог заказов для исполнителя: поиск, фильтры, отклики

Раньше исполнитель видел только те заказы, на которые уже откликнулся (вкладка
«Мои отклики»), плюс случайную подборку из 4–6 карточек в Ленте. Найти заказ по
тематике, бюджету, району или дате было нельзя. Добавили отдельный раздел
**`/orders`** — каталог всех открытых заказов.

**Что умеет каталог:**
- **Поиск** по услуге, адресу, категории и номеру заказа.
- **Тематика** — чипы по всем 12 категориям из `lib/jobCategories.ts`.
- **Бюджет** — «от»/«до», причём диапазоны сравниваются на пересечение: заказ с
  вилкой 30–50к находится и по фильтру «до 40к», хотя строго в него не входит.
- **Локация** — подстрока адреса плюс ограничение по расстоянию (до 5/10/20/50 км).
- **Дата публикации** — за сутки / неделю / месяц.
- **Сортировка** — новые / бюджет выше / бюджет ниже / ближайшие / срочные.
- Счётчик найденных заказов и сброс фильтров одним нажатием.

На карточках для исполнителя видно дату публикации и метку **«Отклик отправлен»**
для заказов, на которые он уже отвечал; новый проп `responded` у `OrderCard`
(плюс флаг `showDate`) не меняет поведение карточек в Ленте — по умолчанию оба
выключены.

**Навигация стала роль-зависимой:** у исполнителя пункт «Заказы» ведёт в каталог
(`myOrdersTabHref(role)` в `lib/format.ts` теперь возвращает `/orders` для master),
а его собственные отклики — по ссылке «Мои отклики» в шапке каталога. У заказчика
пункт, как и раньше, ведёт в «Мои заказы». В «Моих откликах» теперь виден ценник и
короткое сообщение отклика и добавлена кнопка «Найти заказы» в пустом состоянии;
ссылки на каталог также добавлены в Ленту («Все заказы») и в раздел «Создать».

Логика фильтрации вынесена в чистые функции `lib/orderSearch.ts`; при пустых
фильтрах результат детерминирован (текущее время читается только при реально
выбранном периоде), поэтому страница остаётся статически рендерящейся — как и
`/specialists`, без hydration mismatch.

Проверено программно: `npx tsc --noEmit` без ошибок и успешный `next build`
(22 маршрута, новый `/orders`); на production-сервере `/orders` отдаёт 200 и в
серверном HTML сразу есть шапка, счётчик и поле поиска.

## Портфолио исполнителя: отдельная страница, фото, проекты, отзывы

Заполнить работу в портфолио из «Создать» было неудобно: карточка в кабинете
показывала краткий список, а полноценное оформление пряталось в общем разделе
специалистов. Теперь у исполнителя есть отдельная страница **`/portfolio`**
(ссылка «Работа в портфолио» на `/create`, кнопка «Моё портфолио» в его карточке
в каталоге и плитка «Портфолио» в `MasterProfilePanel`).

- **Анкета и статистика** — профессия, город, опыт, цена «от», рейтинг, число
  отзывов и работ; данные берутся из `masterProfile` и синхронизируются с записью
  `SPECIALIST_ME` в каталоге специалистов.
- **Добавление работы** — название, описание, категория, год, цена, срок, до 8
  фото (первое фото становится обложкой, остальные идут в галерею; картинки
  сжимаются через существующий `compressImage`) и галочка **«Выполненный проект»**.
- **Карточки работ** — обложка, галерея, просмотры и лайки, удаление и редактирование
  (`updatePortfolioItem`). У каждой работы в `PortfolioItem` появились поля
  `completed` и `year`.
- **Отзывы о мастере** — блок на той же странице, агрегаты рейтинга и числа
  отзывов пересчитываются при добавлении отзыва.

Страница открыта только роли **Исполнитель**; остальным ролям показывается
короткое объяснение со ссылкой на каталог специалистов.

## Фильтры заказов: сворачиваемая панель и виды работ

Панель фильтров в `/orders` занимала пол-экрана и повторяла те же поля, что и
верхний ряд чипов. Теперь она **свёрнута по умолчанию**: видны только поиск, ряд
тем, счётчик и кнопка «Фильтры N» с числом активных условий. Раскрытая панель
группирует всё по смыслу — тематика, бюджет, локация и расстояние, дата и
сортировка; активные условия вынесены в отдельные pill-метки с крестиком и
общим сбросом.

- **Виды работ (подкатегории)** — `subcategory` в `OrderFilters` и чипы
  `availableSubcategories` в `lib/orderSearch.ts`: показываются только те виды
  работ, которые реально встречаются в открытых заказах, поэтому список не
  предлагает пустых вариантов. Смена тематики сбрасывает выбранный вид работ.
- Кнопки «Другие»/«Смотреть все» больше не дублируют сброс: сброс один, и он
  виден всегда, когда есть активные фильтры.
- Сброс pill-фильтра по периоду возвращает «За сутки/все», а не пустое значение —
  иначе фильтр по дате переставал отдавать результат.

## Шапка: «Сообщество» снова видно

В desktop-шапке пункты меню и поиск жили в одной строке: при ширине около
1264 px пункт «Сообщество» уезжал под поле поиска и становился недоступен.
`DesktopTopNav` разделён на две строки — логотип, поиск и действия сверху,
навигация снизу отдельной строкой с горизонтальной прокруткой на узких
экранах. Высота шапки выросла до ~91 px, поэтому sticky-блоки на страницах
(`/feed`, `/specialists/[id]`, `/projects/[id]`) переведены с `top-24` на
`top-28`. Проверено в браузере на 1024 и 1264 px: все 7 пунктов меню видны,
перекрытия с поиском нет.

## Лента: меньше дублей и мёртвых кнопок

Главная страница повторяла одну и ту же информацию в разных блоках, а часть
элементов ничего не делала. Что изменилось:

- Убрана левая колонка «Разделы» с восемью кнопками без обработчиков — она
  дублировала меню шапки.
- Убраны неработающие переключатели «Для вас» / «Популярное» в заголовке, а
  фильтр по темам перенесён из верхней части страницы в блок «Знания и идеи»,
  к которому он и относится.
- Блок «Проекты, которые сохраняют» и карточка-советAdvice объединены с
  оставшимися блоками: проекты теперь представлены одним крупным проектом, у
  которого есть ссылка «Все проекты», статьи показаны одним блоком, а совет
  профессионала, повторявший статьи, удалён.
- Карточка обсуждения и «Популярные материалы» остались в боковой колонке в
  единственном экземпляре — раньше оба блока дублировались в основной колонке.
- Счётчик «активных заказов» в «UMELO сегодня» считает реальные открытые заказы
  из стора, а не константу; у карточек специалистов в сайдбаре убраны лишние
  превью-фотографии, у блока заказов — кнопка «Показать ещё».

## Миграция localStorage больше не сбрасывает роль

`migrate` в сторе возвращал полностью «чистое» состояние с `role: "customer"`,
поэтому любое повышение версии persist выкидывало исполнителя обратно в
«Заказчика» вместе с его анкетой и откликами. Теперь миграция обновляет
каталог (специалисты, работы, отзывы, статьи) на свежие сиды и сохраняет данные
пользователя: роль, авторизацию, личные данные, анкету мастера, заказы,
отклики, сообщения, избранное и баланс тикетов.

Проверено программно: `npx tsc --noEmit` без ошибок; в браузере на 1024 и
1264 px все пункты меню шапки видны и не перекрываются поиском.

## Специалисты и портфолио

Раздел «Специалисты» перестал быть статичной страницей с четырьмя константами —
это теперь полноценный каталог на данных стора со сквозным сценарием
«профиль мастера → каталог → карточка специалиста → портфолио → предложение
работы», как описано в `Logic.MD`.

**Модель данных** (`lib/types.ts` + `lib/mockSpecialists.ts`):
- `Specialist` — публичный профиль исполнителя: специализация, город и
  расстояние, рейтинг и число отзывов, опыт, работы, услуги, инструменты,
  подтверждение документов, время ответа. 8 демо-специалистов.
- `PortfolioItem` — работа в портфолио с обложкой, галереей, ценой, сроком и
  счётчиками лайков/просмотров (`views` самоисцеляется от `NaN` так же, как у
  заказов). Работы текущего мастера живут в том же массиве с
  `specialistId: SPECIALIST_ME` — единый источник, как «Вы (блогер)» у
  контентных ролей.
- `SpecialistReview` — отзывы. При добавлении отзыва агрегат рейтинга
  специалиста пересчитывается средневзвешенно, поэтому профиль не расходится
  со списком отзывов.
- `MasterProfile` — профессиональная анкета текущего мастера (отдельно от
  общих `PersonalData`).

**Каталог `/specialists`** — поиск по имени/специализации/услуге, фильтр по
направлениям, сортировка (рейтинг / отзывы / опыт / близость), карточки со
ссылкой на профиль и кнопкой «Предложить работу». Страница остаётся статически
рендерящейся: `?orderId=...` читается на клиенте после монтирования, поэтому
весь каталог виден сразу, без Suspense-заглушки.

**Детальная страница `/specialists/[id]`** — витрина профиля: статистика,
«о специалисте», направления, инструменты, портфолио (открывается в модальном
окне с галереей и лайком, просмотр увеличивает счётчик), отзывы, и заказчик
может оставить свой отзыв звёздами. Сбоку — действия: «Предложить работу»
(для заказчика) и «Написать»; просмотры профиля растут при каждом заходе.

**Профиль мастера в кабинете** — вкладка «Мастер» (была «Анкета»,
`components/MasterProfilePanel.tsx` вместо `MasterAnketa.tsx`): специализация,
направления и инструменты тегами, опыт, цена, подтверждение документов и
управление портфолио — добавление работ с загрузкой и сжатием обложки на
клиенте и удаление. «Создать → Работа в портфолио» у мастера ведёт прямо на
`/cabinet?tab=extra`, плюс добавлен пункт «Мои предложения».

**Общий `components/ProposeWorkModal.tsx`** вынесен из каталога и
переиспользуется каталогом и детальной страницей — сценарий «Предложить
работу» в одном месте. Правило `Logic.MD` соблюдено: предложение не создаёт
новый заказ, а выбирает один из уже открытых (или конкретный, если пришли со
страницы заказа).

Попутно: в `tailwind.config.ts` объявлены цвета `sage`/`sage-soft` — они уже
использовались в разметке (`text-sage`, `bg-sage-soft`), но не были заданы, и
классы молча не работали; исправлены две ошибки типов в `app/chats/[id]`,
ломавшие `next build`.

Проверено программно: `npx tsc --noEmit` без ошибок и успешный `next build`
(21 маршрут); на запущенном production-сервере `/specialists` и
`/specialists/sp-1` отдают 200 и содержат данные специалистов прямо в
серверном HTML (каталог, портфолио, отзывы, кнопки действий).


## Новая вкладка «Мои данные» в Личном кабинете (общая для всех ролей)

Добавили `components/PersonalDataPanel.tsx` — общий раздел личных данных,
одинаковый для всех пяти ролей, включая администратора (у него из кабинета
остаётся только эта вкладка — остальные три ему не нужны, вместо них ссылка
на панель `/admin`).

Поля, как просили: никнейм, почта, телефон, дата рождения, VK, Telegram.
Дополнительно добавили часто встречающиеся в профилях полей: **фото профиля**
(с загрузкой и сжатием на клиенте), **имя и фамилия** (отдельно от никнейма —
никнейм публичный, имя может понадобиться для верификации), **город**,
**WhatsApp** (третий типичный мессенджер в России рядом с VK/Telegram) и
**«О себе»** (короткая био-строка).

Модель — новый тип `PersonalData` в `lib/types.ts` + `personalData`/
`updatePersonalData` в сторе. Форма работает с локальным черновиком
(`useState`) и пишет в стор только по кнопке «Сохранить» — чтобы не дёргать
localStorage на каждое нажатие клавиши при вводе.

Проверено программно: у заказчика в кабинете стало 4 вкладки (было 3), у
администратора — только «Мои данные» плюс ссылка на панель, без Статистики/
Избранного/Подписки (они ему не нужны). Заполнил и сохранил никнейм — после
полной перезагрузки страницы значение осталось (реально пишется в
localStorage, не только в состояние компонента).

## Разделены Профиль и Личный кабинет

Профиль и Личный кабинет — теперь два разных экрана с разной ответственностью,
как и просили: Профиль отвечает за вход/регистрацию, Кабинет — за просмотр
информации по роли.

**Идея унификации** (чтобы не писать 4 разных кабинета с нуля): один
конфигурируемый по роли набор компонентов вместо четырёх бесповторных
реализаций.

- **`/profile`** — мок-форма входа/регистрации (email + пароль, реального
  бэкенда нет, но интерфейс и стейт авторизации настоящие — `isAuthenticated`/
  `authName`/`login`/`logout` в сторе), переключатель ролей (это по сути и
  есть выбор типа аккаунта) и одна ссылка «Открыть личный кабинет».
- **`/cabinet`** — новая страница с вкладками, набор которых зависит от роли:
  - Заказчик: Статистика / Избранное / Подписка
  - Исполнитель: + Анкета (перенесена сюда из Профиля)
  - Блогер: + Контент (переиспользует уже готовый `BloggerDashboard` —
    ничего не продублировано)
  - Продавец: + Анонсы (переиспользует `SellerDashboard`)
  - Администратор: у него вместо кабинета — панель `/admin`, ссылка туда.

**Общие для всех ролей компоненты** (одинаковые в кабинете любой роли, не
копипаста):
- `components/StatsPanel.tsx` — статистика с настоящими графиками
  (`recharts`): разбивка по статусам заказов/контента столбчатой диаграммой,
  просмотры, а для блогера — рейтинг среди авторов (топ-10/50/100 по сумме
  лайков×3 + просмотров, `lib/ranking.ts`).
- `components/FavoritesPanel.tsx` — новая сквозная функция «Избранное»:
  кнопка-сердечко на карточках статей/рекламы в Ленте (`favoriteArticleIds`
  в сторе), сохранённые материалы показываются в этой вкладке — одинаково для
  всех ролей.
- `components/SubscriptionPanel.tsx` — баланс билетов + переключатель
  подписки (перенесены сюда из Профиля, тоже общие для всех ролей).
- `components/MasterAnketa.tsx` — анкета мастера, вынесена в отдельный
  компонент (была в Профиле).

**Убрано дублирование**: раньше формы блогера/продавца жили во вкладке «Мои
заказы» (Контент/Анонсы). Теперь эта вкладка навигации у них сразу ведёт в
`/cabinet` (`myOrdersTabHref` в `lib/format.ts`), а старый путь `/my-orders`
для этих ролей просто редиректит туда же — интерфейс живёт в одном месте, а
не в двух одновременно.

**Лайки** — новое поле `likes` у статей, кнопка на детальной странице
(`/articles/[id]`), влияют на рейтинг автора у блогера.

Проверено программно: мок-вход по email работает; в кабинете у каждой роли
рендерится правильное число вкладок (3 у заказчика, 4 у остальных); переход
на вкладку «Контент»/«Анонсы» показывает настоящую форму публикации, а не
заглушку; переход на `/my-orders` у блогера/продавца реально редиректит на
`/cabinet`; добавление в избранное на Ленте появляется в кабинете; лайк на
детальной странице статьи увеличивает счётчик. 0 ошибок в консоли браузера
за весь прогон проверок всех четырёх ролей.

## Единый масштаб карточек + стрелки прокрутки во всех блоках Ленты

Раньше карточки статей (`w-64`, 256px) и рекламных баннеров (`w-72`, 288px)
были разной ширины — визуальный ритм сбивался при взгляде на ленту целиком.
А «Заказы в ожидании исполнителя» вообще жили в статичной CSS-сетке (не
`ScrollRow`), поэтому стрелок там не было в принципе — не потому, что баг,
а потому что для них не было общего компонента прокрутки.

1. **`PromoCard` и `OrderCard` приведены к ширине `ArticleCard`** — теперь
   все три типа карточек ровно 256px, лента выглядит единообразно
   независимо от того, статья это, реклама или заказ. `OrderCard` получил
   тот же проп `fullWidth`, что и `ArticleCard`, — на будущее, если

## Исправлена ошибка гидратации (Unhandled Runtime Error)

Блок «Заказы в ожидании исполнителя» перемешивался через `Math.random()` прямо во
время рендера (`useMemo`). Next.js сначала рендерит страницу на сервере, потом
React «гидрирует» её на клиенте, сверяя, что оба рендера дали одинаковый HTML —
а `Math.random()` на сервере и на клиенте выдаёт разные значения, поэтому порядок
карточек не совпадал, и React ронял ошибку `Text content does not match
server-rendered HTML`.

Исправлено: теперь и на сервере, и при самом первом рендере на клиенте (до
гидратации) список заказов показывается в одном и том же детерминированном
порядке (без перемешивания), а собственно случайная подборка формируется уже
**после** монтирования компонента в браузере, через `useEffect` — это происходит
позже гидратации и больше не может её нарушить. Проверено прогоном 5 полных
перезагрузок страницы в браузере — 0 ошибок в консоли; перемешивание при этом
продолжает работать как раньше.

## Исправлен NaN у просмотров и пустая строка вместо адреса

Заказы, созданные до того, как в модель добавили поля `address`/`views` (см.
предыдущую итерацию), хранились в localStorage без этих полей. Просмотр такого
заказа вызывал `undefined + 1 = NaN` в `incrementViews`, и это `NaN` затем
навсегда сохранялось в состоянии — счётчик показывал буквально «NaN» вместо
числа, а адрес — пустую строку.

Исправлено в двух местах:

1. **`incrementViews` в `lib/store.ts` теперь самоисцеляется**:
   `(Number.isFinite(o.views) ? o.views : 0) + 1` — если поле повреждено или
   отсутствует, следующий же просмотр заказа приводит его к нормальному числу
   вместо продолжения накопления `NaN`.
2. **Отображение стало защищённым** — на странице заказа и в «Моих заказах»:
   просмотры показывают текст «нет просмотров», если значение невалидно или
   равно нулю (а не «NaN» и не пустоту); адрес показывает «не указана»/«адрес
   не указан», если поле пустое, а не пропадает молча.

Проверено программно: воспроизвели точный сценарий — вручную вписали в
localStorage заказ без полей `address`/`views` (как у реального старого
заказа) и убедились, что на странице такого заказа нигде не показывается
«NaN», адрес корректно показывает «не указана», а после первого же захода
счётчик просмотров самоисцеляется и показывает нормальное число вместо
дальнейшего накопления `NaN`.

## "Мои заказы" — крупнее фото, адрес, дата, просмотры и отклики

Карточки заказчика в «Моих заказах» переработаны под общий визуальный язык
сайта и дополнены информацией, которой раньше не было в модели данных:

1. **Фото увеличено** с 64×64px до 96×96px, скругление приведено к `rounded-2xl`
   (как у карточек в Ленте, а не более мелкое `rounded-xl`, что было раньше).
2. **Дата публикации** — `formatOrderDate()` в `lib/format.ts`, формат
   «29 июля 2026». Специально не сравнивали с текущей датой при рендере (не
   писали «сегодня»/«вчера») — это то же самое соображение, что и с
   `Math.random()` в перемешивании заказов: сравнение с `new Date()` (текущим
   моментом) при рендере недетерминировано между сервером и клиентом и может
   вызвать hydration mismatch. Формат всегда зависит только от сохранённого
   `createdAt`, не от "сейчас".
3. **Адрес объекта** — добавили как обязательное поле в `Order` (`address`) и
   в мастер создания заказа (шаг «Объект», перед площадью). Показывается в
   «Моих заказах» и на странице заказа. **Мастеру точный адрес виден только
   после того, как заказчик одобрил его отклик** (`order.status === "matched"`)
   — до этого видно лишь примерное расстояние, как и в самой Ленте. Заказчик
   видит свой адрес всегда.
4. **Оценочная стоимость** — вилка бюджета оформлена как та же плашка-«ценник»
   (`price-tag`), что используется на карточках заказов в Ленте, вместо
   обычного текста — единообразие с остальным сайтом.
5. **Счётчики просмотров и откликов** — добавили поле `views` в `Order` и
   экшен `incrementViews` в сторе; страница заказа увеличивает счётчик при
   каждом заходе (`useEffect` при монтировании). В «Моих заказах» оба счётчика
   показаны иконками (глаз — просмотры, самолётик — отклики) с правильным
   русским склонением («1 отклик» / «2 отклика» / «5 откликов» —
   `pluralize()` в `lib/format.ts`; раньше везде было грамматически неверное
   «1 откликов»).

Как и с билетами/лимитом откликов, счётчик просмотров считается на клиенте без
дедупликации по пользователю/сессии — в реальном приложении это была бы
серверная логика.

Проверено программно: реальный размер миниатюры (96×96px), рост счётчика
просмотров с 34 до 37 после трёх заходов на страницу заказа, корректная
блокировка кнопки «Далее» в мастере без заполненного адреса и её разблокировка
после ввода, а также то, что заказчик видит адрес всегда, а мастер — только
после одобрения отклика.

## Скрыт некрасивый скроллбар у горизонтальных блоков

Ряды тем, превью статей и спецпредложений прокручиваются горизонтально, но в
некоторых браузерах (особенно Chrome/Edge на Windows) под ними виден нативный
скроллбар с кнопками-стрелками по краям — выглядит чужеродно на фоне остального
интерфейса. Добавили класс `.no-scrollbar` в `globals.css`
(`scrollbar-width: none` для Firefox + `::-webkit-scrollbar { display: none }`
для Chrome/Safari/Edge) и применили ко всем четырём горизонтально
прокручиваемым блокам (темы на Ленте и на `/articles`, превью статей,
спецпредложения). Сама прокрутка колесом мыши / трекпадом / свайпом продолжает
работать как обычно — скрывается только визуальный трек, не функциональность.
Проверено через `getComputedStyle` (`scrollbar-width: none` применился) и
эмуляцией прокрутки колесом (`scrollLeft` меняется).

## Правки пятой итерации — адаптивная десктопная версия

Важное уточнение: PWA и «обычный веб-сайт» — это не взаимоисключающие вещи. PWA —
надстройка над сайтом (manifest + service worker для установки на экран и офлайн-кэша),
а не отдельная архитектура. Ничего не переписывали — просто добавили десктопную
раскладку поверх существующего сайта, PWA-возможности остались как есть.

1. **Верхнее горизонтальное меню для десктопа** (`components/DesktopTopNav.tsx`,
   видно от `lg`-брейкпоинта и шире) — логотип, ссылки на 4 раздела, город, баланс
   билетов (для заказчика/исполнителя), кнопка «Разместить заказ». Нижний таббар —
   мобильный паттерн (удобен пальцем, неудобен мышью), поэтому на десктопе он
   скрывается, как и мобильные шапки каждой страницы.
2. **Лента — полноценная десктопная версия**: сетка заказов 2→4 колонки, статьи и
   спецпредложения из горизонтального скролла превращаются в статичную сетку (нет
   смысла скроллить контент мышью так же, как пальцем на телефоне). Круглая кнопка
   заказа скрыта — её роль выполняет кнопка в верхнем меню.
3. **Мастер создания заказа — двухколоночная десктопная раскладка**: слева —
   кликабельный список всех 7 шагов со статусами «пройден / текущий / впереди»
   (можно вернуться на любой пройденный шаг одним кликом, а не жать «Назад» семь
   раз), справа — контент шага в карточке. На шаге выбора категории — 3 колонки
   вместо 2, используем освободившееся пространство.
4. **Остальные страницы** (Мои заказы, Чаты, Профиль, Админка, страница заказа/чата)
   не переделаны с нуля дизайном, но адаптированы так, чтобы не выглядеть сломанными
   на широком экране: контент центрирован в разумную максимальную ширину (768px),
   лишние мобильные отступы убраны. Это сознательно оставлено на следующий проход —
   когда будет ясно, что общий подход (верхнее меню + двухколоночные флоу) устраивает,
   имеет смысл проработать и их индивидуально (например, чаты — в двухпанельном виде
   «список + переписка», как в Telegram Web).

Всё проверено не только визуально, но и программно (Playwright): переключение
мобильной/десктопной навигации по брейкпоинту, переходы между шагами мастера через
боковую панель, блокировка перехода на непройденные шаги, ограничение ширины контента
на «нередизайненных» страницах.

## Правки четвёртой итерации — упорядочили главный экран

1. **Кнопка «+Заказ» → круглая FAB справа-снизу.** Убрали текст, оставили только
   иконку плюса — это устоявшийся паттерн (Avito, Ozon и похожие сервисы), пользователь
   уже понимает его без подписи. Кнопка `fixed` (не пропадает при скролле) и выровнена
   по правому краю мобильной колонки, а не всего окна браузера — на широком экране
   она не улетает в правый угол физического монитора.
2. **Статьи и реклама разнесены по отдельным блокам** с собственными заголовками
   «Статьи и новости» / «Спецпредложения». У рекламных карточек теперь свой,
   визуально отличимый стиль — широкий баннер с текстом поверх фото на градиенте
   (`PromoCard`), а не такая же карточка, как у редакционной статьи. Это сразу
   считывается глазом как «это реклама», без необходимости читать бейдж.
3. **«Заказы рядом с вами» → «Заказы в ожидании исполнителя», случайная подборка
   из 4.** Раньше блок показывал все заказы подряд (включая уже найденные —
   `matched`), теперь только те, что реально ищут исполнителя, причём каждый визит
   в ленту — случайные 4 из общего пула (кнопка «Другие» пересобирает подборку
   вручную). Так на видном месте оказываются разные заказы, а не всегда одни и те
   же самые свежие.

## Правки третьей итерации — роли, контент, номера заказов

1. **Четыре роли** — Заказчик, Исполнитель, Блогер видны в обычном переключателе
   ролей (Профиль). **Администратор — скрытая роль**: 5 быстрых тапов по логотипу
   UMELO в шапке ленты разблокируют 4-ю кнопку роли в профиле.
2. **Экономика билетов и подписки**:
   - у Исполнителя — **3 бесплатных отклика в день**, дальше каждый отклик списывает
     1 билет с баланса (или бесплатно, если активна подписка);
   - Заказчик тратит **1 билет**, чтобы предложить работу конкретному мастеру
     (кнопка «Предложить работу» в списке откликов на его заказ);
   - баланс и переключатель подписки — в Профиле («Пополнить на 5» — демо-кнопка,
     в реальном приложении это была бы оплата).
3. **Блогер** — форма публикации статьи (заголовок, тематика, описание, обложка) в
   Профиле, список своих статей с удалением и продвижением в топ ленты (стоит
   3 билета, списываются с баланса).
4. **Администратор** — отдельная панель `/admin` с тремя вкладками: Заказы (удаление),
   Статьи (удаление + переключение «топ»), Пользователи (демо-список, бан/разбан/удаление).
5. **Лента с контентом** — над списком заказов появились карточки статей блогеров,
   новостей и рекламы (с пометкой «Топ», если продвинуто). 8 сгенерированных тематик
   с фильтром: Ремонт и дизайн, Инструменты и техника, Стройматериалы, Договоры и
   право, Кейсы проектов, Новости рынка, Акции поставщиков, Как выбрать мастера.
6. **Номер заказа** — формат `XKPQ-48213` (4 буквы + 5 цифр через дефис). Выбрана
   **латиница без визуально похожих символов** (без 0/O, 1/I/L) вместо кириллицы из
   исходного примера — так номер проще продиктовать по телефону и ввести на любой
   раскладке клавиатуры. На главном экране есть строка поиска заказа по номеру.

## Что упрощено в этой демо-версии (честно, чтобы не вводить в заблуждение)

- Один браузер = один «пользователь»: переключение роли в профиле — это переключение
  точки зрения для демонстрации сценариев, а не авторизация разных аккаунтов. Список
  пользователей в админке — статичный мок для интерфейса, не связан с реальными
  сессиями.
- «Мои заказы» у Исполнителя показывает заказы, на которые он откликался в этом же
  браузере — в реальном приложении это была бы серверная выборка по account ID.
- Каталог `/orders` фильтруется и сортируется полностью на клиенте — пагинации,
  геопоиска по реальным координатам и серверного полнотекстового поиска пока нет.
- Списание билетов и бесплатный лимит считаются на клиенте и хранятся в
  localStorage — их легко обойти через консоль браузера. Для продакшена эта логика
  обязательно переезжает на сервер.
- Оплата билетов/подписки — кнопки-заглушки без реального платёжного шлюза.

## Что нового в предыдущих итерациях

- **Бренд UMELO**, зелёный логотип (домик) + оранжевый акцент в интерфейсе.
- **Категории работ** — 12 категорий, 36 подкатегорий, 51 услуга (11 категорий из
  вашего `job_category.json` + добавленная «Клининг и вывоз мусора»).
- **Мастер создания заказа** — 7 шагов: категория → подкатегория → услуга → объект
  (до 1000 м² + «более 1000 м² — расчёт индивидуально») → бюджет (за работу и
  отдельно за м²) → срок в днях → описание (обязательное) + фото/видео + документы
  (.pdf/.doc/.docx) → проверка и публикация.
- **Отмена заказа** — крестик у активного заказа в «Моих заказах» с подтверждением.
- Сжатие фото на клиенте + защита localStorage от переполнения (QuotaExceededError).

## Как запустить локально

Понадобится **Node.js 18.18+** (лучше 20 LTS). Проверить версию:

```bash
node -v
```

Дальше в папке проекта:

```bash
npm install
npm run dev
```

Откройте **http://localhost:3000** — приложение само перенаправит на `/feed`.

Чтобы собрать production-версию:

```bash
npm run build
npm run start
```

## Как попробовать новые роли и админку

1. Откройте вкладку **Профиль** — переключитесь между «Я заказчик» / «Я исполнитель» /
   «Я блогер», чтобы увидеть разный интерфейс (форма отклика, форма статьи и т.д.).
2. Чтобы разблокировать роль **Администратор**: на вкладке **Лента** быстро нажмите
   на логотип UMELO в шапке 5 раз подряд — в Профиле появится 4-я кнопка роли.
3. В роли Администратора на Профиле появится кнопка «Открыть панель администратора»
   (`/admin`) — там можно удалять заказы, статьи и управлять пользователями.
4. Чтобы проверить билеты: переключитесь на «Я исполнитель» и откликнитесь на
   4 разных заказа — на первых трёх отклик бесплатный, четвёртый спишет билет с
   баланса (виден в Профиле).
5. Номер заказа виден на странице самого заказа (кнопка с иконкой копирования) и в
   списках «Мои заказы» / «Мои отклики». Ввести его для поиска можно в строке на
   Ленте.

## Дизайн

- Белый фон, графитовый текст (`#2B2D31`), акцент — оранжевый `#FF6B1A`, вторичный —
  зелёный `#1F8A55` из лого UMELO (подкатегории, теги тематик).
- Заголовки — Rubik, текст — Manrope. Оба поддерживают кириллицу, подключены через
  `next/font/google` (нужен интернет при первой сборке — шрифты кэшируются локально).

## Следующие шаги для реального MVP

1. Подключить бэкенд (Node.js + PostgreSQL), реальную авторизацию и многопользовательские
   аккаунты вместо переключателя ролей в одном браузере.
2. Перенести всю экономику билетов/подписки на сервер + подключить платёжный шлюз
   (ЮKassa/СБП) вместо демо-кнопок пополнения.

4. Добавить настоящую геолокацию (Яндекс.Карты/2GIS) и push-уведомления мастерам.
5. Настоящую модерацию статей администратором перед публикацией в ленте.
